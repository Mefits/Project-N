# N — архитектура будущего онлайн-боя

Статус: принято направление развития (2026-11-26); реализация и техническая пригодность пока не подтверждены. Документ — постоянное архитектурное ограничение для новых игровых подсистем, не отдельный игровой milestone. Текущий приоритет анимации и приёмка владельцем остаются в силе (см. [PLAN](PLAN.md), [Animation Lab](ANIMATION_LAB.md)).

## 1. Цель и границы

- Первая сетевая цель — отзывчивая дуэль 1 на 1 через P2P, без обязательного содержания собственных игровых серверов. Локальная игра, AI, запись и PvP используют одну боевую симуляцию.
- Сохранять выразительность движения, опору, перенос веса, контакт, хитстоп, прерываемые атаки, наземные/воздушные серии. Не заменять фактические контакты абстрактными попаданиями ради сетевой простоты.
- Rollback с предсказанием ввода — предпочтительная стратегия для прототипа, а не доказанная возможность. Детерминизм, стоимость пересчёта, устойчивость к сети необходимо измерить.
- На текущем этапе не добавлять сетевые библиотеки, лобби, matchmaking, рейтинг, античит, отдельный сервер или новую версию игрового движка. Не переписывать проверенный бой ради абстрактной архитектуры. Не менять Toolkit.
- Публичный соревновательный рейтинг и доверенная экономика не входят в первую P2P-версию: ни один из двух недоверенных клиентов не может гарантировать честность результата.

## 2. Фактическая исходная архитектура

Проверено по main, игровой baseline 0.10.1 и существующая лаборатория 0.10.2+:

- [project.godot](../project.godot) задаёт 120 физических тиков/с; [motor.gd](../game/motor.gd) и [impact_reaction.gd](../game/impact_reaction.gd) используют DT = 1/120. Тайминги атак, реакции, опоры и hitstop уже завязаны на этот шаг.
- [arena.gd](../game/arena.gd) считывает локальные клавиши в словари команд для двух бойцов и вызывает World.advance(dt, left, right). Это уже частичное отделение источника команд от боевой логики.
- [world.gd](../game/world.gd) содержит World.tick(left, right), фиксированный порядок обработки, два Motor, два Jab, два Rig, контакт/защиту и хитстоп. World.advance — адаптер реального времени с аккумулятором, а не интерфейс повторного расчёта.
- Rig не является чисто декоративным: World._contact использует прежнюю и текущую ударную точку, грудь и таз цели, sweep и порядок разрешения контактов. Углы гибридной реакции могут влиять на Rig и на дальнейший бой.
- [lab/recording.gd](../lab/recording.gd) записывает команды и кадры для диагностики. Наличие повторяемого сценария и визуальных снимков не доказывает возможность полного save/restore или одинакового результата на двух машинах.

### Решение о частотах

| Слой | Направление |
|---|---|
| Боевая симуляция | Сохранить существующие 120 Гц (8.33 мс/тик) |
| Отрисовка | Цель 60 FPS, независима от тиков |
| Логические кадры команд | Проверить 60 Гц как вариант (два тика на кадр); исходно сохранить точность ввода 120 Гц |
| Отправка пакетов | Независимый cadence, пакет может содержать несколько кадров ввода |
| Декоративная физика | Независимая частота, только по результатам профилирования |

Ранее обсуждавшиеся 60 Гц симуляции не являются распоряжением менять baseline: такое изменение потребовало бы отдельной миграции всех таймингов и повторной приёмки контактов/движения. Не терять короткие нажатия при 60 Гц команд или низком FPS. При необходимости передавать два 120-Гц образца в одном пакете вместо удержания одной команды на два тика. Изменение точности ввода — отдельный измеримый эксперимент.

## 3. Границы ответственности

```text
Local input / AI / recorded input / remote input
                        |
                  InputCommand[tick]
                        |
         MatchSession / history / scheduler
                        |
             World.tick(P1, P2) @ 120 Hz
           Motor + Jab + gameplay Rig + reaction
                        |
             State / deterministic events
                  /                  \
      snapshot + hash history     presentation
                                 skin / cloth / VFX / audio
```

Имена новых интерфейсов условны, не требуют создавать все классы сразу. World остаётся единым источником истины для боя. Планировщик владеет номером тика и историей команд, а не правилами попадания. Транспорт передаёт ввод и служебные сообщения, не вычисляет игровой результат.

### InputCommand v0 (предлагаемый контракт)

Номер тика, стабильный слот игрока (в сессии), move (сейчас -1/0/+1), битовые состояния jump, launch, run, jab, heavy, kick, guard. Нейтральная команда полностью определена. Нажатия/отпускания должны воспроизводиться из последовательности состояний; если ввод между выборками нельзя восстановить, потребуется явный edge с однозначной семантикой. Сохранить сочетание W+F, удержание guard и буфер комбо. Не отправлять клавиши устройства, локальное время, pos, hp, готовые попадания или внутренние флаги motor (combo_follow, kick_support и др.).

Нормализация и проверка допустимых значений — на границе ввода; команды одинаково интерпретируются при локальном и сетевом источнике. Отложенные команды сохраняются по целевому тику, включая отсутствующие/предсказанные и подтверждённые. Будущие аналоговые оси/способности — версионированное расширение, не реализация сейчас.

### Симуляция и визуализация

World.tick получает только команды и состояние. Никаких Input.*, wall clock, render delta, await, сетевых вызовов, глобального RNG или зависимости от очередности Node callbacks внутри воспроизводимого шага. Если понадобится случайность — явный RNG со снимком состояния. Стабильный порядок обхода и одинаковые правила одновременных контактов. Хитстоп продвигает номер тика и сохраняет текущую семантику захвата ввода, но не ускоряет физику.

Процедурная опора/IK/поза/реакция остаются внутри игровой симуляции в той мере, в какой влияют на контакты, pushbox, баланс, переходы или следующие тики. Новые состояния переноса веса, фиксации стоп, инерции и переходов должны быть восстанавливаемыми, если влияют на бой. Декоративная деформация, ткань, волосы, растеризация, камера и эффекты — только представление, не источник игровых фактов. Визуальная коррекция при rollback не должна изменять игровые хитбоксы, подменять контакт или портить опору; проверять совпадение видимого удара и механического контакта.

## 4. Состояние, снимки и проверка детерминизма

Первый технический шаг — инвентаризация mutable state и формальная семантика snapshot S[t]: полное игровое состояние непосредственно перед применением команд тика t. Сохранять и восстанавливать обе стороны атомарно.

- World: ticks, freeze/frozen_ticks, флаги режима и правила матча, счётчики и данные последнего контакта, всё, что читается в будущем или нужно подтверждённым событиям.
- Motor: pos/velocity/facing, grounded/launched/pursuing/slammed/diving, timers, стопы и swing/anchors, gait/guard phase, takeoff, latch, next_foot, и прочие изменяемые поля.
- Jab: hp, kind/age, connected/contact_hit, буферы, latch и guard edges, block/parry/hurt, transition_pose и реакция (angles, speeds и др.).
- Rig: сохранённые точки, включая контактную геометрию предыдущего тика, либо доказуемо точное восстановление; не считать, что текущая поза всегда однозначно восстанавливается из Motor (особенно при hitstop).
- Новые механики: RNG, состояние арены/правил, таймеры, события и идентификаторы, если они влияют на симуляцию.
- Аккумулятор World.advance, локальное время, транспорт и render state не входят в детерминированное игровое состояние; их жизненный цикл отдельный.

Snapshot — глубокая копия без ссылок на изменяемые массивы/словари/объекты. Явный schema version, фиксированный порядок полей, каноническое кодирование значений для хеша. Не использовать небезопасную десериализацию объектов из сети. Не хешировать сырые неупорядоченные словари, адреса объектов или декоративную позу. Числа с плавающей точкой, Geometry2D, тригонометрия и разная точность сборок могут расходиться: фиксированный DT сам по себе не гарантирует детерминизм. Сначала сравнить точные хеши на поддерживаемых платформах, найти первое различие; не скрывать его приблизительным хешем. Если потребуется, отдельно оценить каноническую квантизацию или fixed-point только критических вычислений, с регрессиями и визуальной приёмкой.

Отдельные тесты: одинаковые входы и начальное состояние дают одинаковый результат; restore/replay на каждом выбранном тике восстанавливает исходную последовательность; воспроизведение не зависит от FPS и частоты пакетов. Проверить на двух процессах, затем на реально разных компьютерах/сборках. Animation Lab — потребитель той же записи, не отдельный движок.

## 5. Rollback и сетевой протокол (гипотеза для прототипа)

1. Обе стороны согласуют версию протокола, совместимый build/ruleset, seed/initial state, слоты и начало матча. Несовместимые версии не начинают бой.
2. Локальный ввод назначается будущему тику с небольшим согласованным input delay. До получения ввода противника используется ограниченное предсказание (кандидат: удержание последнего состояния без создания новых edge-событий; тестировать guard, combo и быстрые нажатия).
3. Хранить кольцевые буферы полных снимков и команд. При отличии подтверждённой команды от предсказанной найти самый ранний несовпавший тик, восстановить S[t] и вызвать World.tick до текущей границы. Не запускать World.advance, отрисовку, звук или частицы на каждом повторном тике.
4. Игровые события имеют стабильный идентификатор (тик + источник + ordinal). Представление различает предсказанные/подтверждённые события, отменяет ошибочные и не повторяет звук/частицы/удары после пересчёта.
5. Периодически сравнивать хеши подтверждённых тиков; при различии сохранить команды, снимки и первый проблемный тик. При выходе за rollback window, несовместимости или устойчивом desync — ограниченная пауза/прекращение матча с диагностикой; не скрывать ошибку телепортацией или доверенным состоянием произвольного peer.

Input packets: session/sequence, диапазон тиков, компактные команды с повтором недавних неподтверждённых кадров, ACK/подтверждения. Обрабатывать потерю, дубликаты, перестановку и запоздалые пакеты. Служебные согласования — надёжный канал, частый ввод — канал без обязательного ожидания повторной доставки более раннего пакета. Ограничить размеры, частоту и допустимое окно тиков; отвергать поддельный слот, неверную сессию и недопустимые значения. Не применять полученные команды к произвольным объектам/методам.

Первый транспортный эксперимент: ENet/loopback/LAN, затем реальный P2P. Прямой ENet не гарантирует прохождение NAT/CGNAT и может раскрывать IP; не обещать универсальное подключение. Если распространение через Steam подходит, проверить Steam Networking/relay/lobbies и совместимость с Godot на этапе транспорта. Ретрансляция/сигналинг возможны без собственных игровых серверов, но это зависимость от сторонней инфраструктуры, не гарантированно бесплатный или бессерверный Интернет. Не связывать ядро с конкретным провайдером.

## 6. Производительность и приёмка

При 60 FPS бюджет кадра ~16.67 мс на всё (обычно два новых тика при 120 Гц). Rollback может потребовать больше тиков в том же кадре: повтор 100 мс истории — 12 тиков, не считая новых. Цель — сохранить запас CPU и исключить растеризацию/декоративную физику из resimulation.

Предварительная тестовая матрица, не гарантии качества:
- RTT 0/30/60/100/150/200 мс; jitter 0/10/30 мс; потеря 0/1/3/5%, отдельно burst/reorder/duplicate. Фиксировать seed эмулятора. Проверить асимметрию задержки.
- Сравнить input delay и глубину rollback, частоту коррекций, длительность resim (p50/p95/p99), полный frame time, пропущенные кадры, CPU/memory, байты/сек. RTT не равен глубине rollback; измерять реальную доставку команд.
- Прогнать обе стороны, одновременные удары, блок/парирование, буфер комбо, хитстоп, launch/pursuit/air slam, падение/вставание, опорные шаги, прерывания атак и новые переходы. Сравнить HP, контакты, геометрию, состояние, визуальные последовательности.
- Кандидат acceptance gate: ноль расхождений подтверждённых состояний в воспроизводимых тестах; ноль двойных игровых событий; плавность и отзывчивость проверены реальными записями; измерен запас времени кадра на выбранном целевом ПК. Конкретные пределы input delay/rollback и hardware target утвердить после измерений. Не обещать отсутствие коррекций при любом пинге.

Если 120 Гц слишком дороги: сначала профилировать, сокращать только ненужные при replay расчёты, оптимизировать снимки/геометрию и визуальные подсистемы; затем сравнивать альтернативный tickrate отдельным экспериментом без изменения baseline.

## 7. Порядок внедрения без торможения разработки

| Шаг | Результат / критерий перехода |
|---|---|
| N0 — сейчас | Документ и ссылка в AGENTS.md; никаких изменений игрового поведения |
| N1 — небольшой совместимый refactor | Единый адаптер команд поверх существующих словарей, тесты идентичности поведения и покадрового ввода |
| N2 — локальная воспроизводимость | Полный snapshot/restore, replay + hash, headless тесты и первый divergent tick; использовать существующий World и Lab |
| N3 — локальный сетевой стенд | Два независимых World, симулятор задержки/потерь, ограниченный rollback, проверка событий и бюджета |
| N4 — сеть | Два процесса по loopback/LAN, затем реальные подключения; cross-machine проверки, handshake и reconnect/abort policy |
| N5 — первая публичная возможность | P2P дуэль по приглашению, подходящий NAT/relay, реальные сетевые и визуальные тесты, явные ограничения честности |

N1–N2 можно выполнять небольшими шагами одновременно с развитием боевых подсистем, если это даёт пользу текущей разработке; N3+ — после готовности стабильной локальной дуэли и отдельной приёмки. Не начинать весь сетевой трек сразу. Не запускать CI только ради документа.

### Правило для каждого будущего изменения

Проверять, где живёт состояние, какие данные нужны для повторного тика, можно ли обработать действие от любого источника команд, влияют ли визуальные данные на контакт и сколько стоит повторный расчёт. Добавлять соответствующие тесты на значимых игровых контрольных точках. Если решение конфликтует с будущим PvP, явно фиксировать компромисс и альтернативы в этом документе, не ухудшать механику молча.

## 8. Открытые решения

Детерминизм между платформами; фактическая стоимость 120-Гц ядра при rollback; формат/частота команд и окно истории; политика коррекции процедурной позы; выбор транспорта и условия relay; минимальное оборудование; доверие к результату публичных матчей. Все требуют экспериментальных данных. Ничто из этого пока не считается реализованным или подтверждённым.
